## P0-3 検索レイテンシ 2.5s → 6.77s

### 測定結果（2026-11-21、同一マシン・release ビルド・cache 無効）

- **v0.31.2 と現行に差は無い。** 12 クエリ交互実行で p50 1,088 ms 対 1,085 ms、p95 1,193 ms 対 1,160 ms。エンジン別 p50 も同等（mwmbl 1,063 対 1,034、wiby 1,086 対 1,084）。
- したがって「2.5s → 6.77s」は**バージョン間の回帰ではなく、単一 IP・エンジン側の応答変動**。この環境では再現しない。
- `bench/local-retrieval/routing-lab` の `latency_mean` は 2,118 ms。6.77 秒の記録はリポジトリに無い。

### 実測で見つかった構造（バージョン非依存・現行コードに存在）

1. **締め切りに張り付く尾。** science カテゴリで p50 が **3,001〜3,003 ms**、20 リクエスト中 **8 件（40%）が 3002〜3003 ms**。値は `search.timeout_limit = 3.0` と一致する。
2. **原因は遅いエンジンの待ち合わせ。** `aggregator::search_inner` は `join_all` で全エンジンの完了を待つ。engine budget は `min(engine.timeout, remaining)` なので、`europepmc` / `arxiv` のような応答しないエンジンが締め切りまで走り、その分だけ全体が延びる。
3. **`timeout_limit` を下げると線形に改善する。** 3.0 → 1.5 で p50 3,003 ms → 957 ms。ただし `unresponsive` が 13 → 16 に増える（品質とのトレードオフ）。
4. **`retries = 0` と `strategy = staged` は効果なし**（p50 3,002 / 3,002 ms）。リトライ倍の仮説は棄却。
5. 遅いエンジンは**タイムアウトでは休止しない**。`FailureKind::Timeout` は `suspension_key()` が `None` で、`record_failure` は連続 2 回で `ban_time_on_fail`（5 秒）にしかならない。成功すればリセットされるので、毎回 3 秒待ち続ける。

### 修正（実装済み、2026-11-21）

1. **並列検索の待ち合わせに上限を入れた。** `search.early_stop_grace`（既定 0.75 秒）。最初のエンジンが応答したあと、次の応答をその猶予だけ待ち、残りは打ち切る。
   実装上の要点: 待ち時間は `tokio::time::timeout` で**未来そのもの**に掛ける。完了後に経過を見る形では、応答しないエンジンが永久に完了せず締め切りまで待ってしまう（最初の実装でこの罠を踏んだ）。
   打ち切られたエンジンはタイムアウトとして報告され、開始した全エンジンがレジストリ順で結果に現れる。
2. **タイムアウトによる休止は既定で無効。** `SearxEngineTimeout = 0`。実測で、休止ありは空結果を 1 件出しばらつきも増えた（p95 1,981 ms 対 1,384 ms）。打ち切りで足りるため、休止は設定した人のみ。
3. **エンジン別の観測を続ける。** `--check-engines` と `bench_latency.py` を nightly で回し、遅いエンジンを設定ではなくデータで入れ替える。

## 上流（SearXNG）由来の 5 問題

比較のための相手ではなく、この実装が引き継いでいる設計上の負債として扱う。

### U1 単一 IP が bot 判定される — 設定では直せない

- 根拠: 1 プロセスが全エンジンを叩く構成。Google は数クエリで CAPTCHA、Brave は too-many-requests、DuckDuckGo も CAPTCHA。データセンター IP は特に悪い。
- この実装で直せる範囲:
  - 同一ホストへの並列度を全ホストで制限（既存 `host_spacing_overrides` の一般化）。
  - 同一クエリの重複排除と共有キャッシュ（既存 `[cache]`）で「無駄打ち」を減らす。
  - 429 / CAPTCHA を受けたら即休止し、**理由と残り時間を結果に出す**（U2 と共通）。
- やらないこと: IP ローテーション・UA 偽装・CAPTCHA 回避。利用規約の問題を技術で迂回しない方針を維持。
- 受け入れ: 30 問連続で、同一エンジンへの同時接続が設定上限を超えない。休止理由が結果に出る。

### U2 suspend の仕様が重い — 実装で直せる

- 根拠: `src/settings.rs:517-525` の既定値が `SearxEngineCaptcha` 86,400 秒（1 日）、`cf_SearxEngineCaptcha` 1,296,000 秒（**15 日**）、`recaptcha_SearxEngineCaptcha` 604,800 秒（7 日）、`SearxEngineTooManyRequests` 300 秒。`settings.toml` に `suspended_times` が無く、利用者から見えない。
- 結果ページは `templates/results.html:89-92` で **エンジン名だけ**を出す。理由も残り時間も出ないため、黙って結果が減る。
- 修正:
  1. `suspended_times` を `settings.toml` に明示（既定値を可視化）。
  2. CAPTCHA 系を指数バックオフ（1 時間 → 6 時間 → 24 時間、上限 7 日）に変更。Cloudflare も同様。
  3. 結果（HTML/JSON）に「休止中・残り時間・理由」を出す。`/stats` と `--check-config` にも出す。
- 受け入れ: 1 回の CAPTCHA で 15 日止まらない。休止が結果ページと JSON の両方で説明される。

### U3 rolling release で semver がなく、既定値が変わる — 実装で直せる

- 根拠: 既定値はコード内（`Settings::defaults`）と同梱プロファイルに直書き。上流は 2026 年 2 月に `suspended_times` の既定を変更した。このリポジトリも 2026-11-03/04/05 にプロバイダーの既定を変更している（`docs/PROVIDERS.md`）。
- 問題: 追随すると挙動が変わり、コピーを凍結すると腐る。
- 修正:
  1. `settings_schema_version` を設定に埋め込み、`--check-config` が版を報告。
  2. 既定値表 `docs/engineering/SETTINGS-DEFAULTS.md` を生成し、CI でドリフト検査（既定値の変更が文書と CHANGELOG に無ければ失敗）。
  3. 上流追従は「既定値のコピー」ではなく「差分レビュー」に統一。追随単位を release note に記録。
- 受け入れ: 既定値を変えるコミットが、文書更新なしでは CI で落ちる。`--check-config` で版が分かる。

### U4 limiter の bot 判定が API 利用と両立しない — 実装で直せる

- 根拠: `src/web/limiter.rs` は上流 botdetection の移植で、**UA 文字列**を判定材料にする。`python-requests` のような UA は bot とみなされ、JSON API で使うなら limiter を切るしかない。
- 修正:
  1. 経路でルールを分ける。`format=json/csv/rss` の API は「IP + レート」だけで判定し、UA では判定しない。
  2. HTML フォームは現行の botdetection 準拠を維持。
  3. 既定値を「API はレート制限のみ」にし、`settings.toml` のコメントで明示。
- 受け入れ: `User-Agent: python-requests/2.x` で `/search?format=json` が 200。HTML は従来どおり。レート超過は 429 + `Retry-After`。

### U5 エンジンの故障が日常的 — 実装で直せる

- 根拠: Yahoo のプロトコルエラー、DuckDuckGo の接続エラーなど個別故障が恒常化。現行は無効化と交換を手で回す。`docs/PROVIDERS.md` に既定無効の理由が日付付きで蓄積している。
- 修正:
  1. 失敗を分類して結果に出す（protocol / connection / parse / blocked）。`raw_content_status` と同じ思想をエンジンへ。
  2. 生存確認コマンド `rustxng --check-engines`（ネットワークあり・CI では実行しない）。エンジンごとに ok / 失敗理由 / 休止残りを一覧。
  3. 恒常メンテを「設定の書き換え」から「自動休止＋理由表示」へ寄せる。無効化の判断は四半期ごとのレビューに集約。
- 受け入れ: 壊れたエンジンがあっても結果が減る理由が分かる。`--check-engines` 1 コマンドで現状が分かる。

## プロファイルの定義と実装のズレ

意図: `standard` = 規約を確認した版、`full` = 規約を気にしない利用者向け。

実測（`--check-config`）:

| profile | 有効エンジン | 意味 |
| --- | --- | --- |
| standard | 34 | 全件に条件付きレビュー記録あり（CI ゲート `check_provider_policy.py` が強制） |
| full | 39 | standard + `yahoo`, `yahoo japan`, `naver`, `keenable`, `fynd`, `exaapi`（キー必須） |
| clean | 0 | 外部検索なし。索引が無ければ `ready=false` |

無効 239 件の内訳:

| 理由 | 件数 | 実装行数 |
| --- | --- | --- |
| 未検証・一度も試していない | **177** | 43,788（`src/engines` の 89%） |
| 利用者の設定が必要（base_url / キー） | 16 | 4,585 |
| bot アクセスを拒否 | 14 | 3,439 |
| 結果を返さない | 11 | 2,141 |
| 理由の記載なし | 10 | 2,079 |
| 規約未確認 | 6 | 1,198 |
| その他 | 5 | 1,260 |

### ズレの正体

`full` が規約を無視して有効化するのは **6 件だけ**。残る 233 件は規約と無関係に無効で、
最大の塊は「誰も試していない」177 件（実装の 89%）。

つまり「規約なんて知らねー人用」を名乗るなら、**規約は無視できているが、未検証は無視できていない**。
利用者から見ると full は「規約を気にしない版」ではなく「規約を気にしない 6 件を足した版」。

### 修正

1. `full` に「未検証」を一括有効化する明示オプションを追加（`--profile full --allow-unverified` 相当）。
   既定の full は現状維持（起動時に有効化済み 39 件と、除外した理由の内訳を表示）。
2. `--check-engines`（U5）で 177 件を一括スイープし、ok / blocked / broken / 要設定 を分類。
   結果を `docs/provider-review-pending.json` に反映し、ok だったものを full に昇格。
3. プロファイルの説明文を実装に合わせる。`full` の README 記述は
   「規約の確認をしない 6 件＋未検証の一括有効化オプション」と書く。
4. 177 件は「不要コード」ではなく「未検証在庫」。P2 Tier 3 の削除判断は、このスイープ結果を見てから。

### 受け入れ

`--check-engines` の結果が 177 件すべてを分類し、`full --allow-unverified` で有効化できる。
既定 full の起動ログに「39 件有効 / 233 件無効（うち未検証 177）」が出る。
